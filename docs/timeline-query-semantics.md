# Timeline 查询语义模型

> 状态：当前正式设计
> 目的：把 Timeline 面向自然聊天的查询语义、连续性推理位置、以及生成落点原则固定下来
> 关联：`docs/timeline-north-star.md`、`docs/timeline-collector-reasoner-interface.md`、`skills/timeline/SKILL.md`

## 1. 这份文档要解决什么问题

Timeline 当前最大的风险，不是工具不可用，而是查询语义还不够干净：

- `now_today` 这类遗留名字容易把“此刻”与“今天到现在的候选范围”混在一起；
- “最近三天”这类内部 preset 容易把真正的时间语义理解偷换成脚本常量；
- “连续性追问”容易被误当成独立路由类，但它本质上只是查询命中后的推理方式；
- “昨晚八点”“昨晚”“最近有什么有趣的事吗”这几类问法，背后的语义结构并不相同，不能再靠零散示例堆叠。

这份文档的目标，就是把这些语义边界收干净。

## 2. 查询类型只有三类

Timeline 面向聊天层时，只应把请求理解成下面三类：

1. `now`
2. `past_point`
3. `past_range`

除此之外，不再额外发明第四类、第五类路由类型。

## 3. `now`

### 3.1 定义

`now` 表示“此刻”或“当前这一小段时间”的状态查询。

它问的不是“今天从零点到现在发生了什么”，而是：

- 现在在哪里
- 现在在做什么
- 现在是什么状态

### 3.2 示例

- “你在干嘛”
- “你现在在哪”
- “你现在什么状态”
- “你刚才不是在打球吗，现在还在吗”

### 3.3 检索方式

虽然语义目标是 `now`，但 collector 可以把 `today_so_far` 当成候选收集范围。

也就是说：

- 语义目标是 `now`
- 候选事实收集范围可以是“今天到现在”

### 3.4 连续性推理

“还在吗”“后来呢”这类追问，不是独立路由类。

它们仍然属于 `now`，只是 reasoner 在判断时必须考虑：

- 旧事实是否仍在持续
- 是否已有更强新事实结束了旧活动
- 是否应该生成新的当前状态

## 4. `past_point`

### 4.1 定义

`past_point` 表示围绕某个明确时间点的查询。

这里的“点”不要求必须是秒级绝对精度，而是用户意图已经指向一个足够明确的时刻。

### 4.2 示例

- “昨晚八点你在做什么”
- “昨天上午十点在哪”
- “2026-03-22 发生了什么”

### 4.3 命中逻辑

`past_point` 不只允许“精确时间相等”命中，还允许“逻辑连续覆盖”命中。

例如：

- 19:50 有 canon 写着在看电视
- 用户问 20:00 在做什么
- 看电视通常不是一个小于 10 分钟就必然结束的活动

此时 reasoner 可以判断：

- 19:50 的事实仍可自然延伸覆盖到 20:00
- 因而 20:00 仍然在看电视

### 4.4 生成逻辑

如果没有可命中或可延续的事实，才进入生成。

生成时也不能只补一句话，而是要先决定：

- 这个时间点合理出现什么活动
- 这个活动在该时段是否自然
- 是否应写入该具体时间点附近的 canon

## 5. `past_range`

### 5.1 定义

`past_range` 表示某个时间段内的整体查询。

它问的不是“某一刻”，而是：

- 一段时间里发生了什么
- 那段时间在忙什么
- 那段时间里有哪些值得提的片段

### 5.2 示例

- “昨晚在做什么”
- “这几天怎么样”
- “最近有什么有趣的事吗”
- “你今天都忙了什么”

### 5.3 关键点

`past_range` 的第一步，不是直接检索，而是先把自然语言理解成一个更精确的时间范围。

例如：

- “昨晚” 可能需要被理解成“昨天晚饭后到睡前”的一段范围
- “今天都忙了什么” 需要被理解成“今天零点到此刻”

这一步必须由 reasoner 参与，不能靠简单枚举规则草率决定。

## 6. “最近”不是独立接口类型，而是 `past_range` 的一种口语时间范围

“最近”是闲聊里非常高频的口语词。

但最终方案里，不应再把它暴露成单独的接口枚举值。

更合理的方式是：

- skill 或 Timeline 内部的 LLM planner 先理解“最近”到底应映射成什么具体范围
- runtime 再消费已经结构化的 `start / end`
- 它本质仍然属于 `past_range`

## 7. “有趣”不是时间问题，而是语义筛选问题

“最近有什么有趣的事吗” 的重点，不只是“最近三天”，还包括“什么算有趣”。

因此 reasoner 必须同时判断：

- 最近三天里是否已有值得提的有趣事实
- 哪些事实更像真人会主动提起的内容
- 如果没有，应该生成什么类型的有趣事件
- 这个事件最合理落在哪一天、哪个时间段、哪个具体时间点

例如生成“看了一本很有趣的书”时，不能只给内容，还要决定：

- 是哪一天
- 大概发生在什么时间
- 是否适合写入晚上、午后、周末等更自然的时段

## 8. 连续性不是路由类型，而是命中与生成时的推理规则

以后项目里不再把“连续性追问”当成一类独立路由。

连续性是下面两类查询里的推理规则：

- `now`
- `past_point`

也就是说：

- “你刚才不是在打球吗，现在还在吗” 属于 `now`
- “昨晚八点你是不是还在看电视” 属于 `past_point`

区别只在于目标时间锚点不同，不在于路由类不同。

## 9. 对 reasoner 的明确要求

reasoner 至少要能输出这些判断：

1. 这次请求属于 `now / past_point / past_range` 哪一类
2. 用户原话里的时间语义应被归一化成什么时间点或时间范围
3. 现有候选事实里哪些可直接命中
4. 哪些可通过连续性逻辑延续覆盖目标时间
5. 哪些候选事实更符合“有趣”“忙”“轻松”等语义筛选词
6. 如果需要生成，应把事实落在哪个合理时间点或时间范围里

## 10. 对 skill 的要求

`skills/timeline/SKILL.md` 应只承担：

- 把自然问法归入三类查询模型
- 选择正确的 Timeline 调用方式
- 告诉模型不要绕过 Timeline

skill 不应承担：

- 自己解析复杂自然语言时间
- 自己判断活动持续多久
- 自己决定什么算有趣
- 自己生成事实

## 11. 对 runtime 的修改要求

后续 runtime 至少应完成这些调整：

1. 公开输入里使用 `now`，不再暴露 `now_today`
2. `resolve_window` 不再解析自然语言，只消费结构化时间输入
3. 自然语言时间归一化由 LLM planner 完成，而不是由脚本关键词枚举完成
4. collector 输出应能支撑点查询、范围查询和连续性覆盖判断
5. reasoner prompt 应显式描述三类查询模型和生成落点规则
6. E2E 应覆盖：
   - “你在干嘛”
   - “昨晚八点你在做什么”
   - “昨晚在做什么”
   - “最近有什么有趣的事吗”
